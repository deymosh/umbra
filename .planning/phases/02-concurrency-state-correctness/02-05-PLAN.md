<objective>
Fix the two `FeedViewModel` mute/pin bugs: LOG-23/BUG-07 (the local-filter mute mirror resolves the active filter by an id that can never match, so it silently never runs) and LOG-24/BUG-08 (the mute and pin writes' `Result` is discarded, so the UI reports success even when the local write failed after publishing).

Purpose: Muting is user-owned moderation state. Today a feed-side mute publishes to the network but never lands in the active filter's local muted set, and a failed local write is reported to the user as success — both leave the user believing they have hidden an author the app is still showing them.
Output: A working active-filter mirror, result-checked mute/pin messaging reusing ProfileViewModel's exact error vocabulary, tests for both the dead-lookup invariant and the message mapping, and the bug tracker closed out for LOG-23 and LOG-24.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| User mute/pin intent → Amber (external signer) → published NIP-51 list | The list update leaves the app for approval in a separate application before anything local is written |
| Published list → local mute/pin state and the active feed filter's persisted muted set | A local write that fails after a successful publish leaves what the user sees out of sync with what the network was told |

| T-02-05-01 | Repudiation | `muteUser` / `togglePin` success messaging | medium | mitigate | The success message is no longer unconditional: a failed local write now surfaces the existing mute/pin error string with the failure's message, so the app cannot tell the user an author is muted while continuing to show that author's notes. Pinned by the failure-mapping tests. |
| T-02-05-02 | Tampering | the newly-live active-filter mute mirror | medium | mitigate | LOG-23's fix activates a write path that was previously dead code, so it is the one genuinely new effect in this plan. It writes only the user's own mute target into the user's own active `FeedFilter` row through the existing `updateMutedAuthors` call — a normal, user-visible, user-removable filter entry editable from the feed-config and profile screens, never a hidden app-side rule. No new filter type, no new default, and no unremovable entry is introduced. |
| T-02-05-03 | Information Disclosure | `result.exceptionOrNull()?.message` rendered into a user-facing string | low | accept | The interpolated text is a local Room/list-write failure message shown in-app to the device owner, not written to logcat, and the expression is character-identical to the one `ProfileViewModel` already ships for the same failure class — D-04 explicitly mandates reusing that vocabulary rather than diverging. No relay URL or third-party pubkey is introduced into the message by this plan. |
| T-02-05-04 | Elevation of Privilege | anonymous-session write guard | low | accept | Both methods keep their existing `canSignWithAmber()` guard as the first statement and their existing early return, so an anonymous read-only session still cannot reach either write path; this plan adds no guard and removes none. |

No new network surface and no new signing surface: the same Amber round trip and the same NIP-51 publish run, unchanged in ordering. The only behavioral addition is that a previously-dead local filter write now executes and that a previously-discarded write result is now surfaced.

<objective>
Move NIP-09 delete off the pre-confirmation apply: `InteractionActionsCoordinator.deleteEvent` must run both its state-removal callback and its cache/archive removal only from `requestSignAndPublish`'s `onSigned` callback, so a rejected or failed Amber signature leaves the visible note list, the in-memory cache, and the encrypted archive all untouched.

Purpose: Delete is the one Amber-signing write in this codebase that mutates state before the signature is confirmed. Every sibling action (toggleMute, togglePin, toggleFollow) already commits only after confirmation; this brings the outlier into line with the dominant pattern rather than inventing a new one.
Output: A confirmation-gated `deleteEvent`, a corrected `ProfileViewModel` call site with its stale known-bug comment removed, and rewritten coordinator tests that pin the new ordering.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| ViewModel → Amber (external signer, via Android intent) | The delete request leaves the app for user approval in a separate application and may be rejected, cancelled, or fail |
| Coordinator → encrypted Room archive and in-memory cache | A local destructive removal of the user's own content is triggered off the back of that external round trip |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-03-01 | Tampering | `deleteEvent` local removal ordering | medium | mitigate | The archive/cache removal moves inside `onSigned`, so a rejected or failed Amber round trip can no longer destroy the user's own persisted content for a delete that was never published. Pinned by the rejected-sign test asserting `deletedEventId` stays null. |
| T-02-03-02 | Repudiation | visible state vs published state | medium | mitigate | The visible note list is filtered only after the signature exists, so the UI can no longer claim a deletion the network never saw. |
| T-02-03-03 | Denial of Service | awaiting cache removal inside `onSigned` before publish | low | accept | The awaited call is a local Room/in-memory delete on `Dispatchers.IO`, not a network round trip, so the added latency before broadcast is bounded by local disk. |
| T-02-03-04 | Elevation of Privilege | owner check on the delete request | medium | mitigate | `deleteNoteUseCase`'s existing owner check stays the first statement and still returns early, so an event authored by someone else is never signed and never removed. Pinned by the retained owner-check test. |
| T-02-03-SC | Tampering | package-manager installs | n/a | accept | No npm/pip/cargo/Gradle dependency is added; the package-legitimacy gate is not applicable. |

No new network surface and no new signing surface: the same `AmberSignerGateway.signEvent` round trip runs, only the ordering of local effects around it changes.
</threat_model>

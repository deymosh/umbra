<objective>
Fix the two EventIngestCache bugs: LOG-21/BUG-05 (snapshotEmitJob is a plain unsynchronized var raced by concurrent flatMapMerge branches) and LOG-19/BUG-03 (a NIP-09 "a"-tag deletion for a non-owned author's cached addressable event is silently ignored because the lookup only consults the Room own-archive).

Purpose: Deleted content that a followed author retracted must actually disappear, and the snapshot emitter must not lose or duplicate an emission under concurrent ingest — both are correctness guarantees the feed rendering path depends on.
Output: An atomically-scheduled snapshot emitter and a two-source addressable-deletion resolver, each pinned by new tests in the existing EventIngestCacheTest.

Assumption-delta checkpoint: **no-change**. The detector flagged "consults the in-memory store alongside ownEventArchive" as a possible singular-to-plural transition. It is not: this is one delete-lookup consulting two data sources that already both exist, matching `EventRepositoryImpl.getLatestAddressableEvent`'s established two-source resolution precedent. No new pluralized identity concept (no second source of truth, tenant, platform, or auth method) is introduced.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Relay → applyIncomingDeletion | A NIP-09 deletion event arrives from an untrusted relay, signed by an arbitrary author, and asks Umbra to remove locally cached content |
| Concurrent ingest coroutines → EventIngestCache shared state | Multiple `flatMapMerge` branches on different real threads mutate the same emit-scheduling state |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-02-01 | Spoofing / Tampering | `applyIncomingDeletion` a-tag branch | high | mitigate | The new in-memory source is filtered by the same `authorPubkey.equals(deletionEvent.pubkey, ignoreCase = true)` check the archive path already enforces, and the downstream `removeCachedEventsAuthoredBy` re-checks author equality per id. Without both, an arbitrary relay-supplied deletion could evict another author's cached content. Pinned by Test B. |
| T-02-02-02 | Tampering | `created_at` upper bound on a-tag resolution | medium | mitigate | The in-memory candidate list is filtered by `createdAt <= deletionEvent.createdAt` before the max is taken, so a stale deletion cannot retract a newer revision. Pinned by Test C. |
| T-02-02-03 | Denial of Service | `cachedEventsMutex` re-entry | medium | mitigate | The in-memory snapshot is taken exactly once, outside the per-coordinate loop, so the deletion path never attempts to reacquire a mutex it already holds — the same deadlock class `EventLruCache`'s synchronous `onEvicted` contract already guards against. |
| T-02-02-04 | Denial of Service | orphaned snapshot-emit jobs | low | mitigate | The compare-and-set schedule cancels the losing lazily-started job, so a concurrent burst cannot accumulate live coroutines on `repoScope`. |
| T-02-02-05 | Information Disclosure | deletion-path logging | low | accept | This plan adds no log line; the existing telemetry log remains counts-only with no event id, pubkey, or relay URL. |
| T-02-02-SC | Tampering | package-manager installs | n/a | accept | No npm/pip/cargo/Gradle dependency is added; the package-legitimacy gate is not applicable. |

No new network surface and no new persistence: the archive half stays behind the existing `OwnEventArchive` seam, and only the signed-in user's own events remain eligible for Room storage.

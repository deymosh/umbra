Create `app/src/main/java/com/umbra/app/data/nostr/AtomicJobScheduling.kt` containing exactly two `internal` extension functions on `AtomicReference<Job?>`, no class, no object, no interface. Imports: `kotlinx.coroutines.CoroutineScope`, `kotlinx.coroutines.CoroutineStart`, `kotlinx.coroutines.Job`, `kotlinx.coroutines.launch`, `java.util.concurrent.atomic.AtomicReference`.

First function `launchIfIdle(scope: CoroutineScope, block: suspend CoroutineScope.() -> Unit): Boolean` — skip-if-already-active semantics. Read the current value into a local; if that local is active, return false without creating anything; otherwise create the candidate with `scope.launch(start = CoroutineStart.LAZY, block = block)` and `compareAndSet` the observed local against the candidate — on success call `start()` on the candidate and return true, on failure call `cancel()` on the candidate and return false. Exactly one compare-and-set attempt, no retry loop, no spin: a caller that loses simply reports that someone else already scheduled. The lazy start is what makes the loser's job impossible to observe — it never executes a single statement.

Second function `launchReplacing(scope: CoroutineScope, block: suspend CoroutineScope.() -> Unit)` returning `Unit` — cancel-and-replace semantics. Create the candidate lazily the same way, `getAndSet` it into the slot, cancel whatever came back, then `start()` the candidate. Creating lazily and starting last is what preserves the existing call sites' cancel-the-old-before-the-new-runs ordering; a non-lazy launch would let the replacement begin before its predecessor was cancelled.

Deliberately do NOT add a third helper for clearing a slot: the take-and-cancel idiom stays written out at each teardown site, matching `cancelPendingInserts` in `EventIngestCache`. Do not add generics, a scheduler class, a `Mutex`, or any blocking primitive. KDoc each function with the semantic it provides and why the lazy start matters, naming no plan, task, phase, decision id, or commit.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Relay transport (Tor) → session scheduling | Relay connect failures arriving from untrusted, remotely-controlled endpoints drive how often retry jobs are scheduled |
| Logout / session teardown → running jobs | `stop()` must terminate every background job that is still fetching the outgoing identity's history over Tor |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-04-01 | Denial of Service | `scheduleRetry` duplicate/orphaned jobs | medium | mitigate | The compare-and-set schedule creates its candidate lazily and cancels it when it loses, so a burst of connect failures — which a hostile or flapping relay can drive — cannot accumulate live retry coroutines on the session scope. Pinned by the eight-way multi-threaded scenario asserting exactly one execution. |
| T-02-04-02 | Information Disclosure | orphaned `userBackfillJob` surviving logout | high | mitigate | Every teardown site becomes a single take-and-cancel on the holder, so `stop()` (the logout path) cannot leave a superseded backfill job running and still fetching the logged-out identity's history over Tor. Previously an overwrite-without-cancel left exactly that job unreferenced and therefore uncancellable. |
| T-02-04-03 | Denial of Service | deadlock or hang from the new scheduling path | low | accept | The helpers take no lock and perform no blocking wait: one compare-and-set attempt with no retry loop and no spin, and no suspension point inside the atomic section. There is no lock ordering to invert and nothing another thread can hold, so neither helper can deadlock, livelock, or hang a caller — a loser returns immediately instead of waiting. No `Mutex` is introduced into `NostrSessionManager` at all. |
| T-02-04-04 | Denial of Service | premature cancellation of an in-flight job | low | accept | `launchReplacing` cancels cooperatively; a job interrupted mid-fetch leaves no partial write, because backfill progress is recorded through `BackfillAnchorStore` only after each completed step, exactly as before this plan. |
| T-02-04-05 | Information Disclosure | scheduling-path logging | low | accept | This plan adds no log line; the existing session logs stay counts-and-status only, with no pubkey, relay URL, or event id. |
| T-02-04-SC | Tampering | package-manager installs | n/a | accept | No npm/pip/cargo/Gradle dependency is added; the package-legitimacy gate is not applicable and no legitimacy checkpoint is required. |

No new network surface, no new signing surface, and no new persistence: this plan changes only how already-existing, already-Tor-routed background jobs are stored, replaced, and cancelled. The one genuinely new state-shape risk — a lock or hang introduced by the conversion — is addressed by T-02-04-03: the chosen shape is lock-free by construction.

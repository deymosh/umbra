# Performance review for Umbra

Don't start from generic "Compose performance tips." Umbra has already had a thorough audit pass (see `AUDIT.md` Part 4 and the master checklist at its end) and most of the obvious wins are in place. Verify current state with `Grep`/`Read` before claiming something is missing — this codebase has surprised past reviews by already having things under non-obvious names (see the table below).

## What Umbra already has (verify before "fixing" these again)

| Technique | Where | Notes |
|---|---|---|
| Burst coalescing for relay event bursts | `EventRepositoryImpl.scheduleCachedEventsSnapshotEmit()` | 250ms batch window (`SNAPSHOT_BATCH_MS`) + `.conflate()` on the raw websocket flow — a common "frame-debounced UI updates" technique among Nostr clients. Don't add a second debounce layer on top. |
| Per-relay cooldown after failures | `UmbraNostrClient.relayCooldownUntil` | Prevents reconnect storms, a common relay-cooldown idea, simpler here (no scoring). |
| Batched profile fetch (no N+1) | `UserRepository.getProfiles(pubkeys)`, used in feed hydration, `ThreadViewModel`, `NostrTextRenderer` mention resolution | Confirmed via grep audit — every call site batches, none loop `getProfile()`. |
| Stable `LazyColumn` keys/contentType | `NotesFeedSection.kt` (`items(notes, key = { it.id }, contentType = { it.kind })`) | Matches the "stable item identity" half of a common Note-singleton trick used elsewhere, achieved via immutable data + explicit keys instead of a mutable object graph. |
| Scroll-aware animation gating | `FeedScreen.kt` — `animateAvatars = shouldAnimateAvatar(listState.isScrollInProgress)` | Avatars stop animating during fling, a real scroll-gating trick already present, seen in other Nostr clients too. |
| Two-tier cache (fast reads + durable) | `ArrayDeque` (L1) + Room (L2) in `EventRepositoryImpl` | Analogous to a common "LRU in RAM + selective persistence" shape, different data structures, same idea. |
| `CompletableDeferred` init gate | `EventRepositoryImpl.initialCacheLoaded` | Cached Room data renders before the relay connection completes — same goal as any fast-cold-start persistence design. |
| Precise per-relay author routing (gossip/outbox model) | `computeAuthorsPerRelay()` / `scopeAuthorsForRelay()` in `EventRepositoryImpl.kt`, applied in `routeFiltersPrecisely()` (called from `applyChannelToRelay()`) | NIP-65 outbox-model routing: each followed author routes to their own NIP-65 write relays (`RelayListMetadata.getOutboxRelays()`), falling back to `DefaultRelays.DEFAULT_RELAYS` when unknown. `feedAuthorsPerRelay: Map<relayUrl, Set<authorHex>>` is recomputed in `activateUserSession()` and reactively refreshed (debounced) whenever a tracked author's kind-10002 arrives mid-session. Applies to `FEED_NOTES` and `FEED_PROFILES_ONDEMAND` (`PRECISE_ROUTED_CHANNEL_IDS`) — a relay covering 3 of your 200 follows is now asked about those 3, not all 200. Requested authors outside the tracked follow set (e.g. a reply/mention author who isn't followed) have no routing data and are deliberately kept unscoped on every eligible relay rather than dropped — see `scopeAuthorsForRelay`'s known/unknown split. No relay-hint-from-tags middle tier (2-tier fallback, not 3-tier) and the result isn't persisted as saved relays — pure ephemeral routing. |
| Shared OkHttp Dispatcher sized for relay-count reality | `NetworkModule.provideTorOkHttpClient()` | OkHttp's `Dispatcher` defaults to `maxRequests=64`/`maxRequestsPerHost=5` — fine for a REST client, but every relay WebSocket is a long-lived "call" from the Dispatcher's point of view (never completes until closed), and this client is also shared with Coil/Media3 per the no-second-client rule. Once verified as a real regression (relay count silently capped at ~64, own relays sometimes starved out, image/video loads stalling behind them) — `maxRequests=1500`/`maxRequestsPerHost=32`, sized with headroom above `UserRepositoryImpl.MAX_TOTAL_DISCOVERED_RELAYS` (1000, a sanity ceiling not an expected count — see that constant's own doc comment, cross-checked against another client's real-device dispatcher config value of 1024). **If a future review sees "stuck at N connected relays" again, check this first before assuming a relay-pool/routing bug** — it's an OkHttp-layer ceiling, invisible in `Relay`/`RelayIssue` domain models. |
| Relay list Room→domain mapping off the main thread | `RelayRepositoryImpl.getAllRelays()` — `.flowOn(Dispatchers.IO)` | `RelayMapper.toDomainModel()` JSON-decodes every relay's cached NIP-11 `relayInfoJson`; with no `flowOn`, that ran on whatever dispatcher collected the flow — `viewModelScope.launch` defaults to `Dispatchers.Main.immediate`, so this was synchronous main-thread JSON parsing on every relay-list emission, scaling with relay count (worse now that the discovered-relay cap is 1000, not 250). If a future review finds a Room-backed `Flow<List<T>>` repository method with per-item JSON/parsing work in its `.map{}` and no `flowOn`, that's the same bug shape. |
| Feed filter Room→domain mapping off the main thread | `FeedRepositoryImpl.getAllFilters()`/`getActiveFilters()` — `.flowOn(Dispatchers.IO)` | Same bug shape as the relay list one above, found in the same general sweep: `FeedFilterMapper.toDomainModel()` JSON-decodes three fields per filter (`mutedPubkeysJson`/`excludedTagsJson`/`excludedHashtagsJson`), collected from `viewModelScope` by `FeedConfigViewModel`, `FeedViewModel`, and `NostrSessionManager` with no dispatch in between. `FeedRepositoryImpl.getFilterById()` (a plain suspend fn, not a Flow) has the same missing-dispatch shape but wasn't fixed here — single-object, only fires on infrequent mute/filter mutations, not a hot path; revisit if it ever shows up as one. |
| Screen-level lambdas rebuilt on every recomposition (ProfileScreen) | `ProfileScreen.kt` — `onEventClickStable`/`onReplyStable`/`onEventReferenceClickStable`/`onDeleteStable`/`onMuteStable`/`onPinStable`/`isPinnedForEventStable`, passed to `notesFeedSection()` | Same class of bug as the FeedScreen/ThreadScreen fixes already in this table, found in the same sweep: `ProfileScreen` collects `ProfileState.replyCounts`/`reactionCounts`/`repostCounts`, which update live from incoming relay events same as the feed, so these inline lambdas were rebuilt (and defeated `EventCard`'s recomposition-skip) on every count change for any visible note, not just on tab/page load. `isPinnedForEventStable` needed `rememberUpdatedState(pinnedEventIds)` rather than a bare permanently-stable `remember{}`, since `pinnedEventIds` is itself a plain `remember(state.pinnedNotes){}` val (not a `State`-delegate read) — capturing it directly in a permanently-stable lambda would have frozen it at its first-composition value. If a future review finds a frequently-recomposing screen with inline lambdas built at a list-composable call site (not per-item inside `items{}`, which is fine), check here for the two established stabilization patterns (`remember(viewModel){}` for plain viewModel calls, `rememberUpdatedState` + permanently-stable `remember{}` for reads of screen-local derived state). |
| Relay-set-change debounce | `NostrSessionManager.start()` — `debounce(RELAY_SET_DEBOUNCE_MS)` before the reconcile `collect` | `connectToEnabledRelays()` reapplies every channel's REQ to every already-connected relay whenever the relay *set* changes (not just newly-added ones) — necessary because routing/precise-scoping can shift for existing relays too. Since discovered relays can now land one at a time in a burst (see `UserRepositoryImpl.saveRelayList()`), an un-debounced relay-set signal turned into a reapply storm: expensive, and some relay implementations respond to a same-subId REQ resent that often with a "duplicate subscription" `CLOSED` instead of the NIP-01-mandated silent replace. 3s debounce coalesces a hydration burst into one reconcile. |
| Pooled on-demand event lookups | `EventRepositoryImpl.fetchEventById()` / `applyEventLookupPool()`, backed by `NostrChannels.EVENT_LOOKUP` (a fixed channel id, not per-event) | Every concurrent `fetchEventById()` caller (quoted notes in a thread, `ViewportImagePrefetchPlanner`) adds its id to one shared pending-id set and reapplies a single REQ per relay carrying all currently-pending ids, instead of each caller opening its own `event-lookup-<id>` subscription. Reuses `subscribeChannel()`'s existing debounce/fingerprint check for the coalescing — no new debounce mechanism. Don't reintroduce a per-id channel id here. |
| Shared ViewModel across nav-graph siblings | `NavHost.kt`'s `Screen.RelayGraph` nested `navigation()` graph wrapping `RelayConfig`/`RelayDetails`/`ActiveSubscriptions`, `hiltViewModel(navController.getBackStackEntry(Screen.RelayGraph.route))` | These three screens share one `RelayConfigViewModel` instance instead of each `composable()` minting its own screen-scoped one — a screen-scoped instance meant every hop between them re-ran `init{}`'s flow collection from scratch and re-delivered a full `relayRequests`/`relayIssues` snapshot synchronously into that screen's first composition. If a future screen cluster shows the same "feels laggy to open, especially after visiting a sibling screen" symptom, check for this pattern (screen-scoped `hiltViewModel()` where a nav-graph-scoped one would let siblings share already-loaded state) before assuming it's a data-layer problem. |

## Where Umbra genuinely differs from other clients' techniques (real gaps, not re-implementations)

- **`UserRepositoryImpl.saveRelayList()`'s discovered-relay auto-add (persisted discovery) and `feedAuthorsPerRelay` (ephemeral per-REQ routing) are two separate, complementary mechanisms — don't conflate them.** The former adds a tracked author's not-yet-configured outbox relays as persisted `Relay` rows (`isDiscovered=true`, capped at `MAX_TOTAL_DISCOVERED_RELAYS`) the moment their kind:10002 arrives, so the relay pool/connection count actually reaches authors whose outbox isn't otherwise in range; the latter (now implemented, see table above) decides, per already-connected relay, which authors' worth of REQ to send it. Discovery grows the pool; routing decides what to ask each member of the pool.
- **No relay reliability scoring.** Some clients pick the smallest useful relay set per query based on historical author coverage/uptime; Umbra's cooldown is binary (in cooldown or not), no scoring. Precise per-relay routing (above) now exists, so this is the natural next step — scoring which of an author's several outbox relays to prefer when more than one is in range.
- **No per-relay connection budget with ephemeral cleanup.** Some clients cap persistent connections plus short-lived ephemeral ones (e.g. 30 persistent + 50 ephemeral) with idle cleanup. Umbra's discovered-relay count has only a sanity ceiling (`UserRepositoryImpl.MAX_TOTAL_DISCOVERED_RELAYS`, 1000 — a "don't let one malicious kind:10002 freeze the pool" bound, not a real-world usage limit; the product decision is deliberately *no* practical cap) but persisted as real relays rather than ephemeral, and every enabled relay gets a real, indefinitely-held WebSocket connection (no idle/LRU eviction) — the OkHttp Dispatcher ceiling above just means that many connections *can* now actually be attempted, not that Umbra manages the resulting cost with a connection budget like that.

## How to run a review

1. `Grep` for the specific claim before writing a finding — e.g. don't assert "no debouncing" without checking `EventRepositoryImpl` first (see table above).
2. For anything you're unsure is a real technique from another client versus assumption, fetch the actual source — `gh api repos/vitorpamplona/amethyst/contents/<path>` or `gh api repos/barrydeen/wisp/contents/<path>` (both public) are the two clients this skill's comparisons were researched against — rather than relying on memory of this skill file, which may drift from upstream.
3. Cross-check any proposed change against `AUDIT.md` Part 2 and Part 4 non-negotiables (`@Immutable` state, `StateFlow` only, no `hiltViewModel()` in list items, `Dispatchers.IO` for DAO calls) — a performance win that violates those is not a win here.
4. Prefer measuring over guessing when the change is non-trivial (e.g. outbox routing): note in the plan what to measure (relay REQ count, cold-start time, dropped/duplicate events) rather than asserting the improvement.
